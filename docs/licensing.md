# 许可策略：MIT → AGPL-3.0 + 商业许可（双协议）

> 状态：**已生效（0.8.0，2026-11-07）**。
> 本文是判断依据与执行清单，不是法律意见；对外签约文本需要律师过一遍。

## 1. 现在是什么

| 版本 | 许可 | 能否改 |
|---|---|---|
| ≤ 0.6.0（PyPI 上已发布的全部 13 个发行版、全部 git tag） | MIT | **不能**。已授出的权利不可回收，改 LICENSE 文件对已发布版本没有法律效力 |
| 0.7.0 | 从未发布 | 不存在。功能开发完成后直接并入 0.8.0，避免一个版本处在两种许可之间 |
| ≥ 0.8.0 | **AGPL-3.0-or-later + 商业许可** | 是 |

这一条决定了整个策略的边界：**你无法让已经拿到 MIT 版本的人付钱**，所以双协议不是为了「向现有用户收费」，而是为了「给未来的商业使用留一个合法入口」。任何以「收回 MIT」为卖点的方案都是自欺。

## 2. 为什么现在切（此刻成本最低，之后几乎切不动）

- 切换时仓库 **0 fork、0 外部 PR、0 外部贡献者**（2026-11-07 实查），版权 100% 在作者手上。
- 双协议的法律前提是「你有权对全部代码另行授权」。只要出现一个没有签署授权声明的外部贡献，那部分代码就永远是 MIT，商业版必须把它剔除或逐人补签——现实里等于切不干净。
- `CONTRIBUTING.md` 已加入贡献授权声明（提交即同意双授权发布），所以从 0.8.0 起收到的 PR 都能被商业许可覆盖。

## 3. 切了什么

### 社区版：AGPL-3.0-or-later

选它而不是 SSPL / BSL / Elastic License 的理由：

- **OSI 认可**。企业法务对「开源」与「源码可见但非开源」的处理完全不同：后者在多数公司的采购政策里直接出局（Redis → Valkey、Elasticsearch → OpenSearch 的 fork 都由这类改许可触发）。
- **内部自用不触发义务**。AGPL 的额外义务只针对「通过网络向他人提供服务」：公司在内网自用、个人自用、拿来改自己用，都不需要公开任何东西。这正是本项目的主场景，所以对现有用户是零影响。
- **对外提供托管服务时才要求提供源码**（§13）。这正是要收费的那一格。

### 商业许可（可购买）

覆盖面按「谁在靠它赚钱」划，不按功能划：

| 场景 | 社区版（AGPL） | 商业许可 |
|---|---|---|
| 个人自用 | 免费 | 不需要 |
| 公司内网自用 | 免费（不分发、不对外服务） | 不需要 |
| 改完自己用，不对外 | 免费 | 不需要 |
| **嵌进闭源产品分发**（NAS 固件、桌面软件、一体机） | 不允许（传染） | **必须** |
| **白标 / OEM** | 不允许 | **必须** |
| **拿它对外提供托管服务（SaaS）** | 允许，但须向用户提供源码 | 免除此义务 |
| 需要 SLA / 私有补丁 / 优先支持 | 无 | 附加支持合同 |

**关键判断：双协议真正打开的是 OEM / 白标 / SaaS 这条路，不是「企业内网私有化交付」。** 后者在 AGPL 下本来就免费，你卖的是实施与责任（见 `dsh-kb-打包售卖可行性` 的路径 A）。所以：

- 对路径 C（OEM / 组件授权）：**加分**，且是唯一能让厂商敢用的形态；
- 对路径 A（企业内网交付）：**中性偏负**——法务看到 AGPL 会多问一轮，解药是同时提供商业许可（他们买许可来绕开 AGPL，而不是买功能）。

## 4. 已经改掉的（0.8.0 清单，逐项可核对）

- `LICENSE` → AGPL-3.0 全文 + 项目版权声明
- `COMMERCIAL.md` → 商业许可范围、计价单位、旧版本说明
- `pyproject.toml` → `license = "AGPL-3.0-or-later"`、`license-files`、AGPL classifier
- `README.md` / `README.zh.md` 的 `## License` 段 → 三段式（社区版 AGPL / ≤0.6.0 仍 MIT / 商业许可入口）
- `CHANGELOG.md` → 0.8.0 条目第一段写许可变更，并声明「旧版本不追溯」
- `CONTRIBUTING.md` → 贡献授权声明（提交即同意 AGPL + 商业双授权）
- `src/dsh_kb/*.py` → 每个文件首行 `# SPDX-License-Identifier: AGPL-3.0-or-later`（企业 SBOM 工具靠这个识别）
- `Dockerfile` → OCI 标签 `org.opencontainers.image.licenses="AGPL-3.0-or-later"`
- `.github/workflows/ci.yml` → `license-headers` job：任何 `src/dsh_kb/*.py` 缺 SPDX 头即失败
- `tests/test_packaging.py` → 断言许可字段与 SPDX 头，防止有人悄悄改回或漏标

## 5. 贡献者政策（已生效）

`CONTRIBUTING.md` 里的原文：

> By submitting a pull request you confirm that you wrote the contribution, or
> have the right to submit it, and you license it to this project under both
> (a) the AGPL-3.0-or-later and (b) the project's commercial license, so the
> maintainer can keep offering both. If you cannot agree to that, please open an
> issue instead of a pull request.

这是 DCO 级别的授权声明，不需要正式 CLA 文本。**没有这一段，双协议在第一个外部 PR 之后就失效了。**

## 6. 必须提前接受的代价

1. **老版本永久 MIT**：任何人都可以拿 ≤0.6.0 的代码做闭源产品，你无权阻止。双协议只锁住 0.8.0 之后的新代码。这就是 Terraform → OpenTofu 的剧本，别指望它不会发生在你身上——差别只在于你的增量是否足够有价值。
2. **企业采用意愿下降**：不少公司政策一刀切禁 AGPL（不是法律问题，是合规成本问题）。你会失去一部分「内网自用」的免费用户，而他们本来是口碑与案例来源。
3. **文档与销售复杂度上升**：每个来问的人都要先解释「你用哪种方式、要不要买许可」。`COMMERCIAL.md` 要让人 30 秒能自己判断。
4. **商业许可需要一个签约主体**：个人也能签，但企业采购通常要走对公。

## 7. 定价接口（商业许可怎么报价）

不给固定价目表，给报价的**计价单位**（客户能听懂、你能算清）：

- **OEM / 固件预装**：按出货设备数或按年平台授权（一次性 + 年费）。
- **闭源嵌入**：按产品线年费，按「使用它的产品数量」而不是「调用次数」。
- **托管 SaaS**：按席位或按收入分成，二者取一，写清审计方式。
- **支持合同**：按年，含响应时限与私有补丁，不承诺 7×24。

报价区间参考（[推测]，基于同赛道企业档实价）：单产品线年费落在 ¥3–15 万；OEM 按设备量的首年授权常见 ¥10–50 万；SaaS 分成 3–10%。

## 8. 如果将来要回退（不建议，但要写下退路）

回退到 MIT 只对**新版本**有效，已按 AGPL 发出的版本仍然是 AGPL。真要回退，动作是：改 LICENSE + pyproject + README + CHANGELOG，并保留 `LICENSE-AGPL` 供旧版本引用。**不要**试图宣称「我们改回 MIT 了所以旧版本也变了」——那在法律上无效，且是舆论灾难。
